# Implementation Plan: Harden Risk Classifier Against Evasion

**Deliverable:** PLAN.md 2.2  
**Date:** 2026-07-05  
**Status:** Ready for implementation

## Summary

The risk classifier in `security/classifier.py` uses naive substring checks that can be evaded through whitespace manipulation, case variation, and improper regex anchoring. This plan hardens the classifier by normalizing whitespace, making checks case-insensitive where appropriate, and fixing regex patterns to use `.search()` instead of `.match()` so they detect patterns anywhere in the command, not just at the start.

**Critical constraint:** This change ONLY raises scores (never lowers). Existing detections must remain intact; we're closing evasion gaps, not loosening security.

## Problem Statement

### Current vulnerabilities in `security/classifier.py`:

1. **Naive substring checks (lines 26-31, 38-39):**
   - `"sudo" in command` misses `sudo\t`, `SUDO`, `s\tudo`, etc.
   - `"rm " in command` misses `rm\t`, `RM `, `rm  -rf`, etc.
   - `"-rf" in command` misses `-RF`, `-r -f`, `- rf`, etc.
   - `"/etc/" in command` and `"/System/" in command` miss `/ETC/`, etc.

2. **Regex patterns use `.match()` (lines 6-8, 12, 16, 20):**
   - `PIPE_TO_SHELL.match(command)` only matches from the start due to `r".*\|..."`
   - Mid-line pipes like `echo foo; wget x | sh` are missed
   - Same issue with `REDIRECT_TO_SYSTEM` and `SUBSHELL_SUDO`

3. **No whitespace normalization:**
   - Tab characters, multiple spaces, and newlines can hide dangerous tokens
   - `sudo\trm` scores 0 when it should score 60

### Examples that currently evade detection:

```python
compute_risk_score("sudo\trm -rf /")           # Returns 0, should be 90+
compute_risk_score("SUDO RM -RF /etc/passwd")  # Returns 0, should be 90+
compute_risk_score("echo hi; curl x | sh")     # Returns 0, should be 50+
compute_risk_score("rm  -rf /")                # Returns 20, should be 50
```

### Root cause

The classifier was written for simple cases but doesn't defend against:
- Attackers/bugs introducing unusual whitespace
- Case manipulation (bash is case-sensitive for commands, but we should normalize for detection)
- Commands where dangerous patterns appear mid-line

## Solution Approach

### 1. Add whitespace normalization helper

Create a private helper function that:
- Collapses all whitespace (spaces, tabs, newlines) to single spaces
- Preserves the actual command content but makes substring checks reliable
- Can be reused by both substring checks and regex patterns

**Note:** The 2.1 dependency introduced `_split_segments()` in `allowlist.py`, but it's for command chaining, not whitespace normalization. We need a new helper in `classifier.py`.

```python
def _normalize_whitespace(command: str) -> str:
    """Normalize all whitespace to single spaces for reliable pattern matching.
    
    Collapses tabs, newlines, and multiple spaces to single spaces so evasive
    spacing (e.g., `sudo\trm`, `rm  -rf`) doesn't bypass detection. Does NOT
    alter the logical content, just standardizes whitespace.
    
    Args:
        command: Raw command string
        
    Returns:
        Command with normalized whitespace
        
    Example:
        >>> _normalize_whitespace("sudo\trm -rf /")
        'sudo rm -rf /'
        >>> _normalize_whitespace("rm  -rf")
        'rm -rf'
    """
    return re.sub(r'\s+', ' ', command)
```

### 2. Make substring checks case-insensitive and whitespace-aware

Update `compute_risk_score()` to:
1. Normalize whitespace before checking
2. Convert to lowercase for case-insensitive matching
3. Use word boundaries where appropriate to avoid false positives

**Before:**
```python
if "sudo" in command:
    score += 40
if "rm " in command:
    score += 20
if "-rf" in command:
    score += 30
```

**After:**
```python
normalized = _normalize_whitespace(command).lower()

if "sudo" in normalized:
    score += 40
if "rm " in normalized:  # Space after rm is intentional (avoid "term", "harm")
    score += 20
if "-rf" in normalized or "-r -f" in normalized:
    score += 30
```

### 3. Fix regex patterns to use `.search()` instead of `.match()`

The current patterns use `.*` prefix to match from start, then `.match()` which is redundant. Change to `.search()` so patterns match anywhere in the string.

**Before (line 6-8):**
```python
PIPE_TO_SHELL = re.compile(r".*\|\s*(ba)?sh\b")
REDIRECT_TO_SYSTEM = re.compile(r".*>\s*/etc/")
SUBSHELL_SUDO = re.compile(r".*\$\(.*sudo.*\)")
```

**After:**
```python
PIPE_TO_SHELL = re.compile(r"\|\s*(ba)?sh\b", re.IGNORECASE)
REDIRECT_TO_SYSTEM = re.compile(r">\s*/etc/", re.IGNORECASE)
SUBSHELL_SUDO = re.compile(r"\$\(.*sudo.*\)", re.IGNORECASE)
```

And update the helper functions (lines 11-20):
```python
def has_pipe_to_shell(command: str) -> bool:
    normalized = _normalize_whitespace(command)
    return bool(PIPE_TO_SHELL.search(normalized))

def has_system_redirect(command: str) -> bool:
    normalized = _normalize_whitespace(command)
    return bool(REDIRECT_TO_SYSTEM.search(normalized))

def has_subshell_escalation(command: str) -> bool:
    normalized = _normalize_whitespace(command)
    return bool(SUBSHELL_SUDO.search(normalized))
```

### 4. Normalize path checks

Update the system path checks to be case-insensitive:

**Before:**
```python
if "/etc/" in command or "/System/" in command:
    score += 30
```

**After:**
```python
if "/etc/" in normalized or "/system/" in normalized:
    score += 30
```

## Implementation Notes

### Why normalize whitespace instead of more complex parsing?

1. **Simplicity:** Regex + substring checks work well for risk scoring
2. **Defense-in-depth:** This is one layer; allowlist is another
3. **Low false-positive risk:** Whitespace normalization preserves command semantics
4. **Performance:** No need for shell parsing overhead

### Why case-insensitive for detection?

While bash is case-sensitive (`SUDO` won't execute as `sudo`), an attacker could:
- Use aliases: `alias SUDO=sudo`
- Have uppercase versions in PATH
- Generate commands programmatically

Better to score high and let allowlist decide, than miss a potential escalation.

### Why `.search()` instead of `.match()`?

`.match()` only checks from the start of the string. The `.*` prefix was a workaround, but:
- Inefficient (backtracking)
- Still fails if we normalize after matching
- Less clear intent

`.search()` is the right tool: "does this pattern appear anywhere?"

### Edge cases considered

1. **False positives:**
   - "rm " requires a space after to avoid matching "term", "harmful", etc.
   - Regex patterns use `\b` word boundaries where appropriate
   
2. **Command chaining:**
   - 2.1 already handles `brew install x && rm -rf /` at the allowlist level
   - This change ensures each segment scores correctly
   
3. **Quoted strings:**
   - Not handling quotes (`'sudo rm'`) as a string is typically safe
   - If an attacker can inject quotes, they can already bypass
   - Future work could strip quotes, but not required for this deliverable

**Before this change:**
- `sudo\trm -rf /` → score 0 (no detection)
- `SUDO RM -RF /etc` → score 0 (no detection)
- `echo; curl x | sh` → score 0 (no detection)

**After this change:**
- `sudo\trm -rf /` → score 90 (sudo + rm + -rf detected)
- `SUDO RM -RF /etc` → score 100 (capped at 100)
- `echo; curl x | sh` → score 50 (pipe to shell detected)

This significantly closes evasion gaps while maintaining backward compatibility.
